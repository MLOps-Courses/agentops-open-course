# 1.4. Providers

!!! abstract "In one glance"

    - **You will:** Install Ollama, pull the Qwen3 model, and get `mise run doctor:model` green so the agent has a model to call.
    - **You need:** The [1.1. Python](./1.1.%20Python.md#what-proves-this-page-worked) checkpoint passing (`mise run check` and `mise run test`, both from `agents/python`).
    - **Time:** about 30 minutes, hands-on.

## Do you need provider credentials now?

No. Run `mise run check:core` and `mise run test` before configuring a model.

Those gates exercise tools, state, security callbacks, MCP, A2A construction, and adversarial cases. They send nothing to a provider and need no Chapter 5 container engine. They also load no `.env`, deliberately: provider configuration can never make an offline gate pass or fail.

You need a model only for interactive `run`/`web`, the persistent A2A server, live ADK evaluation, and the later gateway lab. The required path — local Qwen3 on Ollama — needs no account, no mandatory SaaS, and no provider credential.

## How do you configure local Qwen3?

The typed defaults already point at this path, so configuration is one install and one pull, not four variables to type.

### How do you install Ollama?

Get Ollama from [ollama.com/download](https://ollama.com/download). On macOS and Windows, use the app installer from that page. On Linux, review the official script before running it — the same curl-then-run pattern this repository uses for `mise`, but inspect first:

```bash
curl -fsSL https://ollama.com/install.sh -o /tmp/ollama-install.sh
sh /tmp/ollama-install.sh   # equivalent one-liner: curl -fsSL https://ollama.com/install.sh | sh
```

`ollama serve` must be running before `mise run doctor:model` can pass — the macOS/Windows app and the Linux service start it for you; otherwise start it in its own terminal. With the daemon up, pull the Apache-2.0 open-weight model:

```bash
ollama pull qwen3:4b-instruct
ollama list
```

!!! info "The pull is a one-time download of about 2.5 GB"

    The weights are fetched once and cached on disk, so a slow progress bar is normal on a home connection rather than a sign that the pull is stuck. `ollama list` then shows the pulled model in your local library.

Then verify the path the way CI does:

```bash
mise run doctor:model
```

A passing run exits zero and prints three lines:

```text
model      ready
env        optional .env is absent
ollama     qwen3:4b-instruct ready on 127.0.0.1:11434
```

The `env` line reads `.env available to explicit live/config tasks` instead, once you create a `.env` for the optional Gemini path below.

!!! warning "What a failing check looks like"

    `mise run doctor:model` exits non-zero and its `ollama` line reads `start Ollama and run: ollama pull qwen3:4b-instruct`. That one line covers both causes: the Ollama server is not running, or the model was never pulled. Start `ollama serve`, re-run the pull, then run the doctor again.

`doctor:model` is a stronger check than `ollama list`: `scripts/doctor.sh` requires the `ollama` binary and then probes `http://127.0.0.1:11434/api/tags` with `jq`, failing unless a served model name starts with `qwen3:4b-instruct`. It therefore catches a stopped daemon and a never-pulled model, not just a missing CLI.

`local-ollama` is a non-secret marker that satisfies the OpenAI client contract; it is not an Ollama credential. Chapter 5 changes only `OPENAI_BASE_URL` to `http://127.0.0.1:4000/v1` once the gateway is running.

## Which environment variables select a provider?

The defaults you just used already select local Ollama. You touch these variables only for the optional Gemini path, or for the Chapter 5 gateway swap.

Read off the contract:

- `AGENT_MODEL_PROVIDER` is a two-value enum — `openai-compatible` (the default) or `gemini`. It selects the ADK client; every other provider field is consulted only on its own branch.
- The `openai-compatible` branch reads `OPENAI_BASE_URL` (default `http://127.0.0.1:11434/v1`, direct Ollama) and `OPENAI_API_KEY` (default the non-secret marker `local-ollama`).
- The `gemini` branch reads either `GOOGLE_API_KEY` (AI Studio) or `GOOGLE_GENAI_USE_ENTERPRISE=true` with `GOOGLE_CLOUD_PROJECT` and `GOOGLE_CLOUD_LOCATION` (Vertex via **Application Default Credentials**, the credentials Google's SDKs find on the machine).

## How do you configure native Gemini?

This path is optional and needs a Google account. Create a gitignored root `.env` from the annotated template and add only the variables for your chosen authentication method:

```bash
cp .env.example .env
chmod 600 .env
```

For an AI Studio (Gemini API) key, override the two defaults and add the key:

```bash
AGENT_MODEL_PROVIDER=gemini
AGENT_MODEL=gemini-3.6-flash
GOOGLE_API_KEY=replace-me
```

For Vertex AI with Application Default Credentials on your workstation, use enterprise mode with an explicit project and location instead of a key:

```bash
gcloud auth application-default login
AGENT_MODEL_PROVIDER=gemini
AGENT_MODEL=gemini-3.6-flash
GOOGLE_GENAI_USE_ENTERPRISE=true
GOOGLE_CLOUD_PROJECT=your-gcp-project-id
GOOGLE_CLOUD_LOCATION=global
```

Verify the enterprise path against that same project before using it:

```bash
GCP_PROJECT_ID=your-gcp-project-id mise run doctor:gcp
```

The doctor reads `GCP_PROJECT_ID` or, when it is unset, the active gcloud project; it does not load `GOOGLE_CLOUD_PROJECT` from `.env`. [1.0. System](./1.0.%20System.md) owns the exact ADC probe and remedies. The GKE overlay uses Workload Identity Federation and stores no service-account key.

## Why is the provider called `openai-compatible` instead of `ollama`?

Because the name describes the ADK client contract, not the deployment topology — as `config.py` comments inline where the field is declared. The `openai-compatible` branch builds an OpenAI-protocol client, and whatever speaks that protocol at `OPENAI_BASE_URL` serves it. That is why the one Chapter 5 change is a URL, not a provider:

- `OPENAI_BASE_URL=http://127.0.0.1:11434/v1` points at Ollama directly.
- `OPENAI_BASE_URL=http://127.0.0.1:4000/v1` points at the agentgateway model route, which then owns policy and telemetry in front of the same Ollama.

The application-side `AGENT_MODEL_PROVIDER` never changes across that switch. `build_model` states the same intent: `OPENAI_BASE_URL` chooses direct Ollama or an agentgateway route "without changing application code". Naming the field `ollama` would have baked one topology into a contract that deliberately outlives it.

## What combinations does the validator reject, and why in one message?

A bad provider combination fails at startup, with a message naming the exact variable to fix.

That check is **cross-field validation**: rules that read several settings at once. It runs when `Settings` is constructed, so nothing surfaces as a stack trace deep in a turn.

On the default path neither `openai-compatible` rejection fires: `config.py` defaults and `.env.example` both set `OPENAI_BASE_URL` and `OPENAI_API_KEY`. Blank either value in your `.env` and you get its message — most often this one:

- **`openai-compatible` with a blank `OPENAI_API_KEY`** explains that Ollama and the open local gateway still need a non-empty marker such as `local-ollama` — the OpenAI SDK refuses an empty key even when nothing authenticates it.

`mise run config:check` runs exactly this path and prints the resolved settings with secrets masked.

## What deadline and retry policy does each provider get?

Both branches share the same deadline and retry-count settings: `AGENT_MODEL_TIMEOUT_S=60` and `AGENT_MAX_RETRIES=2`. Gemini also maps `AGENT_RETRY_BACKOFF_S=0.5` explicitly; the OpenAI-compatible SDK owns its exponential backoff timing.

Neither branch accepts SDK defaults for the deadline or retry count. A chat completion is not idempotent: a network failure after inference can make an SDK retry repeat model work, latency, and provider cost. The bounded application retry is a deliberate reliability trade-off and the only retry authority on this edge; the gateway adds none. Only read tools are safe to describe as idempotent. Guarded write actions are never retried.

Owned by [4.5. Guardrails](../4.%20Quality/4.5.%20Guardrails.md).

??? note "Deeper: the exact client wiring on each branch"

    For `openai-compatible`, `ResilientOpenAILlm` builds the client explicitly instead of mutating process-wide environment state:

    ```python
    @cached_property
    def _openai_client(self) -> AsyncOpenAI:
        return AsyncOpenAI(
            base_url=self.openai_base_url,
            api_key=self.openai_api_key.get_secret_value(),
            timeout=self.timeout_s,
            max_retries=self.retries,
        )
    ```

    For `gemini`, the same settings become a google-genai retry policy plus a per-request HTTP deadline expressed in milliseconds:

    ```python
    def _retry_options() -> types.HttpRetryOptions:
        """Map the course retry settings onto the google-genai retry policy."""
        return types.HttpRetryOptions(
            attempts=settings.max_retries + 1,
            initial_delay=settings.retry_backoff_s,
            max_delay=min(settings.retry_backoff_s * (2**settings.max_retries), 30.0),
        )
    ```

    The Gemini `HttpOptions` deadline is `max(1, round(settings.model_timeout_s * 1000))` — seconds converted to the milliseconds that API expects. See [`model.py`](https://github.com/MLOps-Courses/agentops-open-course/blob/main/agents/python/src/agent/model.py). With the defaults (`AGENT_MODEL_TIMEOUT_S=60`, `AGENT_MAX_RETRIES=2`, `AGENT_RETRY_BACKOFF_S=0.5`):

    | Aspect               | `openai-compatible`                       | `gemini`                                         |
    | -------------------- | ----------------------------------------- | ------------------------------------------------ |
    | Per-request deadline | `timeout=60.0` seconds on `AsyncOpenAI`   | `HttpOptions(timeout=60000)` milliseconds        |
    | Attempts             | `max_retries=2` transient retries         | `attempts=3` (`max_retries + 1`)                 |
    | Backoff              | OpenAI SDK's built-in exponential backoff | `initial_delay=0.5`, `max_delay=min(0.5·2², 30)` |

## Where do these variables have to live to take effect?

In the repository-root `.env`. Agent tasks run from `agents/python`, and the model-backed ones load `../../.env` — that relative path is why the file lives at the repository root, not beside the Python code.

[1.1. Python](./1.1.%20Python.md) owns the exact task boundary and explains why deterministic gates load no dotenv. This page only needs you to keep provider overrides in the root file and run `mise run config:check`.

Exporting the same variables in your shell also reaches `Settings()`, because pydantic reads the process environment. You then lose task scoping and mise's dotenv redaction, so prefer the root `.env`.

## How do you protect model data and credentials?

The repository gives each of these a concrete mechanism, not just advice:

- Keep `.env` out of Git and restrict its permissions (`chmod 600`). The `secure` task's Trivy scan is told `--skip-files .env`, so a local secret file never trips the gate — and never becomes a reason to weaken the scan.
- `config:check` and the mise dotenv loader both redact secrets: `SecretStr` fields print as `**********`, and the loader runs with `redact = true`, so a resolved-config dump or task log never echoes a key.
- Never bake credentials into an image, ConfigMap, command example, trace, or screenshot.
- Leave ADK/GenAI message-content capture disabled (`ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false`, its default) unless you have reviewed the data policy.
- Route cloud workloads through identity federation instead of long-lived service-account keys; the GKE overlay uses Workload Identity and stores no key.
- Treat model prompts and tool output as potentially sensitive even in a fictional exercise.

## What proves this page worked?

Prepare one provider path without sending a prompt. For the required local path:

```bash
ollama list
mise run doctor:model
mise run config:check
```

`ollama list` records the installed model identifier. The doctor proves the server exposes the expected tag, and `config:check` proves the agent will resolve the local defaults with secrets masked. On the optional Gemini path, configure `.env` and run `mise run config:check`; do not send a hosted request merely to finish Setup.

**You are done when:**

- `mise run doctor:model` exits zero and its `ollama` line reads `qwen3:4b-instruct ready on 127.0.0.1:11434`.
- You configured no provider variable at all — or, on the optional Gemini path, `mise run config:check` printed your resolved settings with the key masked.
- You have not sent a prompt or attempted a write action; [2.1. First Agent](../2.%20Agents/2.1.%20First%20Agent.md) owns the first conversation.

Continue to [1.5. Workspace](./1.5.%20Workspace.md) when your provider configuration is valid and its scoped doctor passes.
